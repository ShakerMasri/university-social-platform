## Problem and objectives

Academic communication is scattered across general social media. Students struggle to find relevant communities and answers, miss announcements, and repeat questions because earlier discussions are difficult to retrieve.

The project will organize academic interaction, help students discover relevant content, retain reusable discussions across academic years, support direct communication, and offer assistance grounded in accessible sources. Iterative design, functional testing, usability feedback, access-control evaluation, and citation evaluation will provide evidence for the graduation report.

## Specified stack and settled decisions

- Next.js and TypeScript for frontend and backend, PostgreSQL storage, and Prisma data access are specified by the abstract. React and the Next.js App Router are the preferred approach in AGENTS.md. Strict TypeScript and server-side authorization apply.
- Both students and teachers can create communities. The four post types, direct text messaging, in-app notifications, archive, and grounded AI assistant are baseline scope; they are not optional extensions.
- The latest notes settle the direction that everyone participates equally in the shared social space, while teachers have additional authority within their own course communities. Teacher verification and the exact community powers still need definition; this does not grant global authority or automatic priority across the platform.
- University email ownership must be verified. The notes' suggestion that a typed student ID or email proves student status conflicts with the identity rules: neither a typed ID nor a matching domain establishes ownership, current enrollment, or teacher status.
- AI uses authorized content, cites supporting sources, and indicates insufficient information. Teacher identity and popularity alone do not establish truth. Private messages are excluded from retrieval by default; external AI use of private community content needs an explicit privacy decision.
- Complete and evaluate the minimum baseline before implementing later extensions. No service provider, hosting choice, or vector infrastructure has been selected. M1a runtime and application/tool versions are recorded in README and the lockfile.
- M1a uses `/en` and `/ar`, with `/` temporarily redirecting to English. This initial default is reversible; browser-language negotiation is deferred. No separate app name is selected.

### Proposed flow and server permissions

The following records the approved M2-D1–D6 local synthetic direction. Request endpoints accept bounded, validated input; every protected read/write rechecks current database session state. No browser-submitted user ID, verified flag, role or email change can authorize a profile operation.

1. A visitor submits an eligible address and locale. Normalize through the existing contract, enforce exact domain eligibility and atomic limits, then find/create the one account by `emailKey`. Creating a pending row grants no access. Deliver to the preserved stored address for an existing account; capitalization variants must not rewrite its identity.
2. Serialize issuance/replacement for that user. Create a random, digest-only challenge using database time; revoke older outstanding challenges in the same transaction. Send the raw token only through the approved adapter after commit. Bound delivery time; on failure revoke the new challenge and expose a generic retry state. An uncertain provider retry must not mint a second token/send silently: use a provider-supported idempotency key if available, otherwise require a new rate-limited request. No plaintext-token queue is introduced by default.
3. Opening the link displays a confirmation screen; **GET/prefetch never consumes a challenge or creates a session**. Bind it to the initiating browser's temporary state to prevent login CSRF; a link opened elsewhere instructs the user to request a new link there. The confirmation POST validates origin/CSRF, browser binding, token and current target email. Use configured application origin/allowlisted local paths, never an untrusted Host or redirect URL. Keep link secrets out of access logs/referrers and test diagnostics; use a token fragment, `no-referrer`, no third-party assets and immediate URL cleanup. Mobile/cross-device handoff is later work.
4. Under consistent transaction/lock ordering, consume exactly one live challenge, set verification once for a new account, revoke sibling challenges, and create one fresh session together. Returning verified users must also present a new valid login challenge; their original verification timestamp is preserved. If session creation fails, consumption/verification roll back. No account/role upgrade is inferred. Send the session cookie only after commit; if the response is lost, require a fresh challenge rather than permit replay. Replace/revoke the current browser session on reauthentication to prevent session fixation/account confusion.
5. Route a verified user without a profile to setup; save/read only their own minimal profile. A return visit within the live session restores that profile; a return after expiry requires another email challenge but preserves saved data. Logout is a protected POST that revokes the database session before clearing its cookie; replaying the old cookie must fail. A failure to revoke must not be presented as successful server logout.

| Actor / state | Permitted server operations under the recommendation |
| --- | --- |
| Anonymous or pending/unverified account | Request/resend a bounded challenge and confirm possession through the protected confirmation flow. No profile read/write or authenticated content access. A stored user ID is not a credential. |
| Verified user, live session, no profile | Read their own account/setup state, save their required display name, and logout. A fresh session is available only after possession confirmation. |
| Verified user, live session, saved profile | Read/edit their own profile and logout. Email is owner-private and immutable in this slice. |
| Any user targeting another user's identity/profile | Deny reads/writes and account-existence metadata under the owner-only proposal, including direct URLs, supplied IDs, caches and serialized errors. |
| Expired/revoked/unknown session, even with an old cookie | Deny protected reads/writes. Recheck on every request; client state, a hidden form or a prior successful check grants no access. |

For web, propose a host-only `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/` cookie with a production `__Host-` name and expiry no later than the database session. Only a random opaque credential goes into it, with its digest stored server-side; no email/role/profile payload or browser localStorage token. Allow insecure cookies only in an explicit loopback development/test configuration. Use the Next.js cookie API and framework CSRF protections, plus appropriate checks on custom route handlers. Private identity responses must not enter shared caches. These recommendations follow the [Next.js authentication guide](https://nextjs.org/docs/app/guides/authentication), [cookie API](https://nextjs.org/docs/app/api-reference/functions/cookies) and [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html); package choice remains unresolved.

Future mobile: stable IDs and server permission checks remain reusable, but web cookies/links are not automatically a native authentication solution. Choose native secure credential storage, request binding, deep/universal links and revocation transport when a mobile client is designed. Do not add bearer/JWT refresh infrastructure now or pass database credentials to clients.

### Local implementation and verification

`Community` stores a stable UUID, restrictive owner relation, bounded plain-text name/description, public/private visibility and timestamp. `CommunityMembership` has a composite primary key `(communityId, userId)`, restrictive user/community relations and either PENDING or MEMBER status. The generated/reviewed additive `20261010010000_m3_communities` migration creates these records and enums with a supplemental text check in one SQL transaction. It changes no M2 data or applied migration bytes. Owner membership is inserted atomically with creation; owner leave/removal is rejected server-side. No deletion/transfer/visibility-change endpoint exists, and the runtime cannot update or delete community records or reassign membership keys.

The focused server service derives the actor only from the live verified M2 session and rechecks expiry before committing/delivering results. Parameterized [PostgreSQL 18 transaction-scoped shared/exclusive advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS) serialize private-space/member-list reads with membership writes; these locks release at transaction end and require cooperating application callers. Prisma 7.10.0 has no row-lock query option, so these locks avoid granting community UPDATE simply to acquire row locks. A hash collision only reduces concurrency. Account/session locking retains the existing M2 order, then per-user resource-budget and community locks. Every community reader/writer must reuse this policy when later content is added. Unique keys and serialized transitions make join/approval/leave/remove retries safe; approval cannot create a request, and a repeated join cannot downgrade an approved member.

Discovery exposes only approved metadata, the actor's own membership/ownership flags and own creation eligibility. Private direct pages/API reads require current membership; other users receive a generic unavailable result. Owner-only membership APIs and SSR projections check ownership independently of client controls. Display names are plain escaped text, mixed text uses direction isolation, and all community responses use private/no-store caching. The localized interfaces include creation, membership requests, approval/rejection/removal, join/leave/cancel, pagination, safe errors/focus and working/loading/empty states. Profile following/visibility is not consulted to grant community access.

Local operational limits: 8 KiB JSON bodies, 80/1,000 Unicode-code-point name/description bounds, 20-item cursor pages, 50 communities owned and 500 membership/request records per user, and 30 authenticated mutation attempts per 15-minute fixed window. The existing counter table is reused under a distinct digest key; reservations commit separately so rejected owner operations consume budget. Current permissions are checked again in the write transaction. Tune limits with actual usability/abuse evidence before release; no university restriction or retention policy is implied.
